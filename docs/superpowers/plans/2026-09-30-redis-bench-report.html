Redis 장애 부하 측정

Redis가 멀쩡할 때, 죽어 있을 때, 부하 도중 죽을 때 POST /errors가 어떻게 버티는지 측정했어요. 문제 2(요청 도중 500)를 고치기 전의 기준값이에요.

매 실행 순서

  1. Redis를 켜고 헬스 플래그가 돌아오도록 7초 대기
  2. Redis FLUSHALL, Postgres error_logs 비우기
  3. 시나리오별 조작 (아래 표)
  4. autocannon 30초 부하. 같은 service로 계속 보내서 임계값을 넘는 "장애 상황"을 만들어요
  5. 시나리오당 3회 반복, 중앙값 기록

데이터 출처 두 가지

autocannon 결과: 클라이언트 입장의 합계예요. RPS, 지연 분위수, 5xx, 타임아웃.

서버 로그: 요청마다 끝난 시각, 탄 경로(redis / db-fallback), 걸린 시간이 남아요. 이걸 1초 단위로 묶어 아래 타임라인을 그렸어요.

환경: Apple M1, colima VM 2 CPU / 4GB. 레이트리밋 해제, webhook 끔. 절대 성능이 아니라 전후 비교용 수치예요.

요청은 끝난 시각의 칸에 들어가요. 그래서 10초 가까이 멈춰 있던 요청은 Redis가 다시 뜬 칸에 찍혀요. 그래프에 마우스를 올리면 초별 수치가 보여요.

측정으로 확인한 것

버그

Redis가 죽는 순간 요청이 500을 받는다

3회 모두 kill 이후 Reached the max retries per request limit (which is 3) 예외가 컨트롤러까지 올라갔어요. 1회차는 즉시 6건이 500을 받았어요. 2·3회차는 요청이 Redis가 다시 뜰 때까지 약 10초 멈췄다가 실패했어요. 그래프의 빨간 마름모 위치가 이 차이를 보여줘요.

버그

헬스 플래그가 늦게 내려간다

② 2회차는 Redis를 죽이고 7초를 기다렸는데도 플래그가 true였던 것으로 보여요. 실패한 요청의 예외가 Redis 경로에서만 나는 종류였거든요. 원인은 아직 확인하지 못했어요. 첫 요청 50개(= 동시 연결 수)가 전부 Redis 경로로 갔다가 500을 받았어요.

버그

큐 적재는 실패하지 않고 멈춘다

3회 모두 Redis 복구 후 처음으로 알림을 큐에 넣은 요청이 약 7.7초 걸렸어요. 앱의 Redis 연결은 복구됐지만 BullMQ의 별도 연결은 아직 재연결 중이라 queue.add가 기다린 거예요. 지연 그래프 오른쪽의 높은 점이 이거예요.

설계

Redis가 죽어 있는 동안 알림이 한 건도 안 나간다

3회차의 알림 기록은 kill 전 1건(13:10:02)과 복구 후 1건(13:10:29)뿐이고, Redis 중단 구간(13:10:10~13:10:21, UTC)에는 0건이었어요. 그 사이에도 에러 수는 계속 임계값을 넘었어요. 문제 1(fail-open 모순)이 수치로 보이는 부분이에요.

관측

Redis가 죽을 때 로그가 안 남는다

서버 로그에 redis 복구는 6번 찍혔는데 redis PING 실패는 0번이었어요. 에러 이벤트가 헬스 플래그를 먼저 조용히 내려서, 경고 로그가 찍히는 조건을 못 만나요. 장애가 언제 시작됐는지 로그로 알 수 없어요.

비용

DB 폴백은 처리량을 약 45% 깎는다

요청마다 최근 60초 행을 COUNT 하기 때문이에요. ① 중앙값 663 RPS가 ② 366 RPS로 떨어졌어요. 그래도 폴백 중 실패는 없었어요.

미확인

복구 직후 처리량이 몇 초간 떨어진다

2·3회차에서 Redis가 다시 뜬 뒤 몇 초 동안 초당 처리량이 수십~수백 건으로 내려갔어요. 1회차엔 없었어요. 원인은 아직 모르고, 수정 후 재측정 때 다시 볼 거예요.
