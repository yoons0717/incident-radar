Redis 장애 부하 측정

Redis가 멀쩡할 때, 죽어 있을 때, 부하 도중 죽을 때 POST /errors가 어떻게 버티는지 쟀어요. 수정 전 코드(61c2207)와 수정 후 코드를 같은 스크립트, 같은 조건으로 측정해서 나란히 놓았어요.

매 실행 순서

  1. Redis FLUSHALL, Postgres 에러·알림 테이블 비우기
  2. 백엔드 재시작. 프로세스 메모리(메모리 cooldown)가 이전 회차에서 넘어오지 않게 해요
  3. 시나리오별 조작: ② 부하 전에 Redis kill 후 7초 대기, ③ 부하 약 8초 지점에 kill, 10초 뒤 start
  4. autocannon 30초 부하. 같은 service로 계속 보내서 임계값을 넘는 "장애 상황"을 만들어요
  5. 시나리오당 3회 반복, 중앙값 기록

왜 수정 전을 다시 쟀나

9/30에 잰 첫 기준값은 회차 사이에 백엔드를 재시작하지 않았어요. 재시작 여부만 바꿔도 같은 코드의 정상 RPS가 732에서 1037로 움직여서, 그 기준값과 비교하면 조건 차이가 코드 차이처럼 보여요. 그래서 수정 전 코드를 따로 빌드해 같은 스크립트로 다시 쟀어요.

환경: Apple M1, colima VM 2 CPU / 4GB. 레이트리밋 해제, webhook 끔. 절대 성능이 아니라 전후 비교용 수치예요.

지연은 중앙값 RPS 회차의 값이에요. 실패는 5xx와 10초 클라이언트 타임아웃을 합친 건수예요. ①의 약 10% 차이와 ③의 RPS 감소는 원인을 확인하지 않았어요. 정상 경로는 거의 바뀌지 않아서 개선으로 보지 않아요.

③ 부하 중 Redis kill · 1초 단위

Redis가 죽는 순간 무슨 일이 일어나나

Redis 경로로 처리 DB 폴백으로 처리 5xx 응답 알림 발송 Redis 중단 구간

초당 처리한 요청 수

그 1초 동안 가장 느린 요청 (ms, 로그 스케일)

요청은 끝난 시각의 칸에 들어가요. 수정 전 3회차는 Redis 중단 구간에 끝난 요청이 거의 없어요. 요청들이 Redis가 다시 뜰 때까지 멈춰 있다가 +10초 칸에서 한꺼번에 500을 받았거든요. 그래프에 마우스를 올리면 초별 수치가 보여요.

확인한 것

수정으로 바뀐 것, 측정하다 새로 찾은 것

해결

Redis가 죽는 순간에도 500이 나지 않는다

수정 전에는 3회 모두 5xx나 타임아웃이 났어요(2 / 5 / 100건). 수정 후에는 Redis 명령이 500ms 안에 실패하고, 같은 요청 안에서 DB 폴백으로 다시 세서 0건이에요. 최대 지연도 4.6초에서 1.1초로 줄었어요.

해결

Redis가 죽어 있는 동안에도 알림이 나간다

수정 전 ③의 알림은 kill 약 8초 전과 복구 후(+18초) 두 건뿐이었어요. 수정 후에는 kill 직후(+0.2초)에 메모리 cooldown과 직접 발송으로 1건이 더 나가요. ②도 0건에서 1건이 됐어요. 그래프의 초록 삼각형이 알림이에요.

해결

헬스 플래그가 늦게 내려가 생기던 실패가 사라졌다

수정 전 ② 1회차는 첫 요청 50개(동시 연결 수)가 아직 true인 플래그를 믿고 Redis 경로로 갔다가 500을 받았어요. 이제는 Redis 경로가 실패해도 그 자리에서 DB로 다시 세요.

발견

타임아웃된 명령이 Redis 복구 후 다시 실행됐다

ioredis는 보낸 뒤 응답을 못 받고 끊긴 명령을 재연결 때 다시 보내요. 이미 타임아웃으로 실패 처리한 cooldown 락(SET NX EX 300)이 복구 직후 실행돼서, Redis 경로 알림이 5분간 막혔어요. autoResendUnfulfilledCommands: false로 껐어요.

비용

DB 폴백은 처리량을 약 35~40% 깎는다

요청마다 최근 60초 행을 COUNT 하기 때문이에요. 수정 전후 모두 ② 처리량이 ①보다 그만큼 낮아요. 폴백 중 실패는 없어요.

미확인

③ 처리량은 수정 후가 조금 낮다

중앙값 752에서 672로 내려갔어요. 장애 구간 요청을 실패시키지 않고 DB 폴백으로 끝까지 처리하기 때문으로 보이지만, 확인하지는 않았어요.
